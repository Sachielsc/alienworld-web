# AI Orchestration System — Frontend Beautify

Status: **built & smoke-tested 2026-07-31 — awaiting API keys before the first real run**
Based on: `doc/about AI orchestration system for our current project.md` (initial proposal) + Charles' 6-point revision + discussion on 2026-07-30.

## Purpose

A human-supervised, multi-agent workflow for beautifying pages of *Charles' Alien World*. Three roles, three different models. Claude Code orchestrates and is the **only** agent with write permission; the other two seats are strictly advisory.

Secondary purpose, stated explicitly by Charles: this is an **experiment in multi-agent cooperation**. That goal shapes the delegation policy below — the system deliberately hands work out even when the orchestrator could do it faster alone, because observing the cooperation *is* the point.

## Confirmed decisions

| Topic | Decision |
|---|---|
| Orchestrator / implementer | **Claude Code** (Pro subscription). Sole writer — no other model may edit the repo. |
| UI/UX Designer seat | **Gemini 3.5 Flash** by default, free tier. Configurable. |
| Senior Reviewer seat | **Poolside Laguna S 2.1 (free) via OpenRouter** by default. Configurable. |
| Transport | **OpenAI-compatible HTTP** for every seat. One client function; a seat is fully described by `{baseUrl, model, keyEnv, vision}`. |
| Delegation policy | **Always delegate when the seat's connection is solid.** No task-based routing, no orchestrator discretion. Fall back to self *only* on connection failure. |
| Invocation | `/frontend-beautify <absolute path to a .md brief file>` |
| Ordering | **Implement first, then convene the council.** Both seats critique real output, not speculation. |
| Order of work | Build → preflight seats → capture → delegate → judge → revise → report |
| Revision rounds | 1 by default, configurable per run. |
| Verdicts | `ACCEPT` / `REJECT` / `DEFER` + one-line reason. No fabricated confidence percentages. |
| Run records | `doc/ai-orchestration/runs/<page>-<date>.md` |

## Why "implement first"

The orchestrator completes the beautification and deploys it to the local dev server *before* the council is convened, because:

1. A UI/UX critique of a page that is about to change is speculation. A critique of the page **as actually rendered** is evidence-based.
2. A code reviewer reading pre-change code reviews code nobody is shipping. Reading the real `git diff` is the reviewer's actual job.

## Roles

### Orchestrator — Claude Code
Parses the brief, resolves target files, implements, drives Playwright, preflights the seats, packages context, judges suggestions, applies accepted ones, verifies, reports. The only writer.

### UI/UX Designer — Gemini (configurable)
Receives **screenshots at three viewports + rendered markup + the brief's stated goals**. Returns professional design critique: spacing, hierarchy, typography, colour, responsive behaviour, visual consistency.

> **Architectural note.** This seat cannot drive Playwright itself — an HTTP `chat/completions` call is stateless and has no access to the MCP server, which is bound to the Claude Code session. So **the orchestrator acts as the designer's eyes**: it navigates, resizes, and captures, then sends those artifacts to a vision-capable model. A design critique needs to *see* the page at a few viewports, not to explore it interactively.

### Senior Reviewer — DeepSeek R1 (configurable)
Receives the **`git diff`, the full changed files, and relevant `server/routes/*`**. Returns code review: syntax, structure, bugs, regressions, maintainability. Text-only — most free code models lack vision.

## Delegation policy

Per Charles' explicit decision, there is **no routing logic and no orchestrator discretion**. If a seat answers, it gets the work.

Free tiers fail in a specific way — a seat can pass a preflight ping and *then* return HTTP 429 on the real request. So "connection is solid" is defined operationally:

```
preflight ping (10s timeout)
   ↓ pass
real request
   ↓ fail (429 / 5xx / timeout / malformed)
one retry with backoff
   ↓ fail
fall back to orchestrator self-performing that role
```

When the fallback fires, the run report must say so loudly:

```
Designer: SELF — Gemini unreachable (429 after retry)
          ⚠ this critique is NOT independent
```

Without that label the system silently degrades into "Claude with extra steps" and the experiment produces misleading results.

**Quota escape hatch.** Because every run now delegates by default, each run costs free-tier quota. Setting `enabled: false` on a seat — in the brief's frontmatter for one run, or in `config.json` for all runs — skips it without a preflight, and the report records it as skipped rather than unavailable. This economises on a specific run without weakening the default policy.

## Pipeline

### Phase A — Brief
1. Read the `.md` brief at the given absolute path.
2. Resolve target route → file list. State the list before touching anything. Ask rather than guess if the page cannot be identified.

> **Route resolution wrinkle.** Per `client/src/router/index.js`, several routes have **no dedicated view** — `/movies`, `/games`, and everything under `/about/*` and `/workreport/*` are rendered by `ContentPage.vue` fed a content key from the server. So "beautify the movies page" resolves to `ContentPage.vue` + `theme.css`, *not* a `MoviesView.vue`. The skill must handle this case explicitly.

### Phase B — Build (orchestrator alone)
3. **Baseline capture** — screenshot at 390 / 768 / 1440px immediately before editing. Regression reference only; **never sent to any seat**. Costs one Playwright call and zero LLM tokens.
4. Implement the beautification completely, per the brief.
5. Confirm the dev server is up (`npm run dev`), the page renders, and the console is clean. This is the orchestrator's own sanity check, not the council's artifact.

### Phase C — Convene the council
6. **Preflight** both seats. Report status.
7. **Capture — only if at least one seat is live.** Screenshots at 390 / 768 / 1440px, accessibility tree, console log, `git diff`. No live seat means no wasted capture.
8. **Delegate in parallel.**
   - Designer ← screenshots + markup + brief goals
   - Reviewer ← `git diff` + changed files + relevant `server/routes`
   - Dead seat → orchestrator performs that role, labelled `NOT INDEPENDENT`.

### Phase D — Judge & revise
9. Each suggestion gets `ACCEPT` / `REJECT` / `DEFER` + a one-line reason.
10. **Revision pass** — apply accepted items. Distinct from Phase B; the skill must be explicit about which write phase it is in, or the revision pass can drift into re-doing the build.
11. Re-capture the same three viewports. Confirm the revisions landed, the console is still clean, and nothing regressed against the Phase B baseline.

### Phase E — Report
12. Write `doc/ai-orchestration/runs/<page>-<date>.md`: seat status (independent or fallback), every suggestion with its verdict and reason, what actually changed. Present the diff to Charles.

## Invocation & brief format

```powershell
/frontend-beautify "C:\Users\gaide\repos\alienworld-web\doc\briefs\beautify-home.md"
```

The brief body is free-form markdown. Optional frontmatter overrides configuration for that run:

```markdown
---
target: /                    # route, or a view file path
seats:                       # optional per-run override
  designer: { model: gemini-2.5-pro }
  reviewer: { enabled: false }
revisionRounds: 1
---
# Goal
Make the hero feel less cramped on mobile.

# Constraints
- Keep the alien theme
- Don't touch theme.css tokens

# Out of scope
- Navigation layout
```

## Configurability — three layers, last wins

1. `tools/ai-council/config.json` — project defaults
2. **Brief frontmatter** — per-run override
3. CLI flags — `--model`, `--config`, … (see `tools/ai-council/README.md`)

Nothing about any provider is hardcoded. Because every seat speaks the OpenAI-compatible wire format, swapping Gemini→Grok or DeepSeek→GLM is a config edit with **zero code change**. Adding a *third* advisory seat later is also just a config entry.

```json
{
  "designer": {
    "baseUrl": "https://generativelanguage.googleapis.com/v1beta/openai",
    "model": "gemini-3.5-flash",
    "keyEnv": "GEMINI_API_KEY",
    "vision": true
  },
  "reviewer": {
    "baseUrl": "https://openrouter.ai/api/v1",
    "model": "poolside/laguna-s-2.1:free",
    "keyEnv": "OPENROUTER_API_KEY",
    "vision": false
  }
}
```

## Data boundaries

**Delegating publishes code to a third party.** The context builder hard-excludes:

- `.env` — secrets
- `server/data/` — SQLite database, sessions
- `server/protected-content/` — gated content; has no business going to a free-tier endpoint

`config.json` stores only env-var **names**, never key values, and the script never logs a key. `config.json` is safe to commit; `.env` stays gitignored.

**Context budget.** A full package is the target view + `App.vue` + `theme.css` + child components ≈ 1,400 lines / ~15k tokens. Small enough to send whole — no summarisation or file-selection heuristics needed. (`theme.css` at 1,176 lines is the bulk; the views are 23–139 lines each.)

## Known gaps / future work

- **No free OpenAI tier exists.** API access is prepaid credits, separate from any ChatGPT subscription, so GPT cannot fill the Reviewer seat on a free key. OpenRouter fills it instead, and the config makes switching to a paid OpenAI key a one-line change if ever wanted.
- **Independence is only as good as the vendor spread.** Designer and Reviewer are currently different vendors, which is the point. Collapsing both onto Gemini would be simpler but would let them share blind spots.
- **Reusability.** Nothing in the skill is specific to *Charles' Alien World* except the route-resolution notes. Pointing it at another Vue project should require only a new `config.json` and a brief.
