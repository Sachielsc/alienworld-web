# Sub-path Deployment — hobbies.seekschool.nz/alienworld/

Status: **LIVE at https://hobbies.seekschool.nz/alienworld/ since 2026-08-13** — deployed and
verified in production (see *Deployment record* at the end).
Based on: discussion on 2026-08-11 about reusing an existing seekschool.nz subdomain.

The *how* lives in `docs/deployment_guide.md`. This file records the **why** — the two
decisions that reversed mid-discussion, and the audit findings behind them, so neither has
to be re-derived later.

## Confirmed decisions

| Topic | Decision |
|---|---|
| Subdomain | **`hobbies.seekschool.nz`** — a new dedicated subdomain, not the existing `preprod.` |
| Path | **`/alienworld/` sub-path**, not the subdomain root — room for more hobby projects |
| Who owns 80/443 | The **existing host nginx** on the CVM; this repo's `nginx`/`certbot` containers move behind a `standalone` profile |
| Prefix handling | **Express mounts under the prefix**; nginx forwards it intact (does *not* strip it) |
| CDN | **None** — direct `A` record to the CVM, unlike `preprod`/`sandbox` which go through Tencent EdgeOne |

## Decision 1: why not `preprod.seekschool.nz`

The original idea was `preprod.seekschool.nz/hobby/alienworld`. Rejected because `preprod`
already serves another app, which means:

- the session cookie (no `path` set, so defaulting to `/`) would be sent to **every other app
  on that subdomain** — this site has an admin login, so that is a real leak
- we would be editing a server block that already carries live traffic

A dedicated `hobbies.` subdomain removes both. Cost is one DNS A record and one certificate.

## Decision 2: why a sub-path at all

Serving at the **root** of `hobbies.seekschool.nz` needs **zero** code changes — the app
already works that way. The sub-path costs ~80 lines. It was chosen deliberately so other
hobby projects can share the subdomain, each behind its own `location` block and its own
port. Each app scopes its session cookie to its own prefix, so they cannot read each other's
sessions.

**If that plan ever changes, reverting to the root is cheap**: set `base` back to `/`, drop
`BASE_PATH`, and the rest degrades gracefully.

## Decision 3: Express mounts the prefix — nginx does not strip it

This one **reversed during implementation** and is the least obvious choice in the whole change.

The first design had nginx strip `/alienworld/` (`proxy_pass http://127.0.0.1:3010/` with a
trailing slash) and Express keep serving from its root. It works in production, but it breaks
`npm run build && npm start` — the local production check documented in `README.md` — because
the built `index.html` asks for `/alienworld/assets/...` and a root-mounted Express has nothing
there.

So Express now mounts the whole site under `BASE_PATH` via a `site` router, and **nginx is a
plain pass-through** (`proxy_pass http://127.0.0.1:3010`, no trailing slash). Consequences:

- dev, `npm start`, and production all behave identically — no environment-only path juggling
- the nginx config gets simpler, not more complex
- `/` redirects to `/alienworld/` so hitting the container directly still works

**Trap: the trailing slash on `proxy_pass` is what decides this.** Adding one back would
double-strip and 404 everything.

## Decision 4: no CDN — direct A record, not EdgeOne

The other subdomains are CNAMEs to Tencent **EdgeOne** (`*.eo.dnse5.com`), used to keep those
sites reachable from **mainland China**. `hobbies.` skips it: the audience for a job-seeking
showcase is NZ/international, and EdgeOne adds certificate management and SPA cache rules for
no benefit here. It is also cheap to reverse — adding EdgeOne later is a DNS + certificate
change, **not** a code change.

**Consequence — check the security group.** Because `preprod`/`sandbox` arrive via EdgeOne,
inbound 80/443 may be restricted to EdgeOne's IP ranges. A direct `A` record needs
`0.0.0.0/0` on 80/443, or **both the site and `certbot` will fail** (Let's Encrypt validates
over HTTP from its own servers, which are not EdgeOne).

**If EdgeOne is ever put in front of this site**, two things change: TLS moves to an EdgeOne-
managed certificate instead of host certbot, and cache rules must not cache `index.html` —
the hashed files under `/alienworld/assets/` can cache indefinitely, but a cached `index.html`
serves stale asset URLs after every deploy.

## Audit findings — what Vite handles vs what it cannot

Verified empirically with a throwaway `vite build --base=/alienworld/`, not assumed. This is
the part most worth keeping:

| Reference | Handled? |
|---|---|
| `index.html` favicon / vendor CSS / script tags | ✅ auto base-prefixed |
| `url()` in `client/src/assets/css/theme.css` | ✅ **20/20** auto-prefixed |
| `<img src="/images/…">` inside `.vue` templates | ✅ auto-prefixed |
| `<img src="/images/…">` inside `client/src/content/**/*.html` | ❌ **invisible to Vite** |

The content fragments are imported with `import.meta.glob(..., { query: '?raw' })` — they are
opaque strings at build time, so Vite never rewrites them. Fixed at the injection point in
`ContentPage.vue` with a `withBase()` replace, which keeps it to one place instead of editing
3 content files.

### Two traps inside that rewrite

1. **Only `src` is rewritten, never `href`.** In-content links like `<a href="/about/worklog">`
   are intercepted by `ContentPage.onClick()` and handed to `router.push()`, and vue-router
   prepends the base itself. Rewriting `href` too would produce
   `/alienworld/alienworld/about/worklog`.
2. **`url(...)` is deliberately left alone.** The only occurrence,
   `url("../images/bgi-dark.jpg")` in `workreport/report14.html`, is sample text inside a
   `<pre><code>` block, not a real reference — the file does not even exist.

## The prefix is set in two places and they must agree

| Where | Setting | When |
|---|---|---|
| `client/vite.config.js` | `base = '/alienworld/'` | **build** time — compiled into asset URLs |
| `docker-compose.yml` | `BASE_PATH: /alienworld` | **runtime** — read by `server/index.js` |

Changing the path requires changing both **and rebuilding the image**. The client base cannot
be read from the environment.

## Deployment record — 2026-08-13

Deployed to `hobbies.seekschool.nz/alienworld/` via direct `A` record, no CDN. Certificate from
Let's Encrypt, `Aug 12 → Nov 10 2026`, renewed weekly by cron (Mondays 04:00 **Asia/Shanghai**,
which is 08:00 NZ).

### What differed from the plan

Four assumptions turned out wrong. They are the useful part of this record.

1. **The security group was never the blocker.** 80/443 were open to `0.0.0.0/0` all along. The
   ports answered *Connection refused* because **nothing was bound to them** — no host nginx
   existed. A firewall block drops packets and the client times out; a refusal is a TCP RST,
   which only the host sends. That distinction was misread, and the evidence (an instant
   failure, not a timeout) had been visible from the start.
2. **No host nginx existed at all.** The guide originally led with a host-nginx path, on the
   belief that this CVM proxied `preprod`. It does not — `preprod` is EdgeOne → COS. The stack
   runs its own nginx + certbot containers.
3. **Compose is the standalone binary at `/usr/local/bin/docker-compose`** (v2.40.3), not the
   `docker compose` plugin — `docker compose` returns *unknown command*. Cron needs the full
   path; cron's `PATH` excludes `/usr/local/bin`.
4. **`nginx/bootstrap/` replaced a manual file swap.** The first draft told the operator to `mv`
   the TLS config aside on the server. It is now a committed directory selected by
   `NGINX_CONF_DIR`, so nothing is edited on the box.

### The one real weakness found

An unset `SESSION_SECRET` made the app crash-loop — correct fail-fast behaviour. But **nginx
crash-looped with it**, because nginx resolves upstream hostnames at startup and `app` did not
exist in Docker's DNS. One bad `.env` therefore took down the web server too. See
`docs/todo/future_work.md` §7.
